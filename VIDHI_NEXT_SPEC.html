Build specification · paste-ready instruction for an AI coding agent

Vidhi Next — a standalone, advanced statistical-validity firewall

A deterministic governance layer that decides whether a claim about Indian official survey statistics may be said at all — before any model writes a word — and proves the decision with a cited rule, a verified source cell, and a frozen hash. This document captures the intent, the current system, and a complete, phased plan to rebuild it as an independent project.

Author of the base system: Ajay Choudhary (MSAI @ Plaksha University). Spec derived from aip-lab/vidhi (Vidhi Guardian v1). Prepared as a hand-off instruction for the next build.

How to use this document

This is the single source of truth for the rebuild. It is written to be handed to an AI coding agent (or a new engineer) as the authoritative brief. Everything the agent needs — mission, current architecture, the decoupling constraint, the target design, module contracts, the exact deterministic rules, the evaluation bar, and the definition of done — is here.

Suggested workflow. (1) Read §1–§3 to lock the intent and the independence rule. (2) Start with the Master kickoff prompt in §12 to bootstrap the repo. (3) Build Phase P0 in §4, checking each phase's acceptance test in §8 before moving on. (4) For each phase, paste that phase's prompt from §12. (5) Never accept a claim without a measured number (see the ethos in §1).

Assumptions baked into this spec (change them explicitly if you disagree, before coding):

  • The new project is a new top-level repository/folder, not a folder inside aip-lab. It must not import anything from aip-lab/ or the aip toolkit.
  • It stays Python-first, CPU-only, offline-capable, and free to run (no GPU, no paid API needed for the core path).
  • The first corpus remains MoSPI Indian official statistics (PLFS, HCES, TUS, MIS) because that is where the current evidence and rules live; the architecture must stay survey-agnostic.
  • The core promise is unchanged: rules judge, models translate; freeze before retrieval. The “advanced” work extends coverage, safety calibration, extraction robustness, performance and explainability — it does not relax the guarantees.

1. What we are trying to do #

1.1 The one-liner

“Find the number is solved. Whether you are allowed to say it is not.”
Government statistical assistants (e.g. MoSPI’s StatsDoc pilot) help users retrieve official figures. Vidhi Next is the governance layer that checks whether a claim is statistically defensible — and stops the user, with a cited rule, when it is not.

1.2 The problem we are solving

Generative AI over sovereign statistics fails at governance, not retrieval. Retrieval over official PDFs is largely a solved engineering problem. The unsolved problem is that a fluent model will happily:

  1. Hallucinate statutory definitions. Example: expanding MPCE as “Mean Per Capita Expenditure” when the statute says “Monthly Per Capita Consumption Expenditure”.
  2. Do unguided cross-round arithmetic. Example: quoting ~40% MPCE growth between HCES 2011-12 and 2023-24 without warning that the 2023-24 round switched from single-visit paper canvassing to three-visit CAPI with a restructured item list — a methodological break that makes a raw level comparison invalid.
  3. Be subverted by its own evidence. Retrieved document chunks can carry instructions (prompt injection via RAG), so a poisoned passage can flip a verdict.

A fourth, quieter failure: on a slice it has no data for, an unconstrained RAG system guesses instead of saying “I have no verified figure for this slice.”

1.3 The thesis (why deterministic)

You cannot fix a probabilistic system with more probabilistic system prompts. The decision — is this claim allowed? — must be made by versioned, transparent, deterministic rules, before generation. The model may only translate a question into structure, and phrase an already-frozen answer. It may never move the verdict.

1.4 The six non-negotiable guarantees

These are the soul of the system. Every advanced feature must preserve all six, and each must have an automated test (see §8).

1 · Rules judge, models translate

No LLM output can change a verdict. Verdicts come only from deterministic, versioned rules.

2 · Freeze before retrieval

The verdict hash — SHA-256(claim + decision + reason + rules) — is computed before any document text is read. Poisoned chunks cannot move it. (“Safety-B”.)

3 · No cosine threshold is safe

Danger-pair and paraphrase similarity ranges overlap on every embedder we measured. Cache reuse requires exact match on all critical fields, not a similarity score.

4 · No PASS without provenance

A numeric answer requires a verified store row whose value traces to cited source text. Anything else is WARN or REFUSE.

5 · Ambiguity is never contradiction

Post-retrieval checks only contradict on same round + same filters + same measure basis + same unit. When in doubt, do not downgrade silently — and never upgrade.

6 · Honest coverage

Uncovered slices return WARN_NO_DATA plus a live coverage note naming the requested slice and the closest verified context — never endorsed, never guessed.

1.5 The ethos: “No number, no claim”

“The prompt got better” scores zero. A deliverable is a measured, reproducible claim with a confidence interval: “verdict accuracy 100/100 [Wilson 95% CI 0.963–1.000] on the 100-query golden set, reproducible offline in one command.” A negative result, honestly measured, is full credit. A fabricated number is a hard failure.

1.6 Who this is for

Journalists, fact-checkers, legislative researchers, statistical agencies, and any AI assistant that needs a trustworthy authority for “what can I safely claim from this data?” Vidhi Next should be usable both as a standalone service/CLI and as an MCP tool that other agents call as a governance oracle.

2. What exists today (Vidhi Guardian v1) #

The reference implementation lives in aip-lab/vidhi/. It works, it is measured, and it is the behavioural baseline the rebuild must match or beat. This section is the inventory you are cloning the behaviour of, while discarding the coupling.

2.1 End-to-end pipeline

Question

2.5 Data, provenance and the audit gate

  • Store (store.json): the built truth artifact, generated — never hand-edited. Each row carries survey, round, indicator, measure, geography, state, residence, sex, age_group, activity, value, unit, source_document, table_or_section, verification_status, provenance{extractor, pdf_sha256, …} and a per-row audit_note.
  • Audit gate (audit.py): every candidate value must be traceable to its cited source text (value near its anchor word or state name). Untraceable values or duplicate row IDs fail the build. A dual-source rule requires API and PDF parsers to agree exactly on any overlapping row.
  • Current coverage: 173 verified rows — HCES state MPCE (both imputation legs, all states/UTs, rural+urban), PLFS national LFPR/WPR/UR, TUS activity minutes. Measured store coverage of the golden set ≈ 54/173 (31.2%).
  • Comparability rules (data/vidhi/comparability_rules.yaml, v3): each rule carries verdict, sub_code, reason_code, caveat_quote (verbatim), source_doc, source_page, active. Rules are data, so the frozen hash binds the exact YAML version.
  • Survey taxonomy (data/vidhi/survey_metadata.yaml, v3): in-corpus surveys with indicators, measures, allowed disaggregations; plus reference_only surveys (kept so cross-round comparisons hit Comparability rather than blunt out-of-scope).

2.6 Retrieval, service, agent, MCP, demo

  • Retrieval (post-freeze, untrusted): curated excerpts first, then a hybrid BM25 + dense (RRF) pass over a full-PDF index; bi-encoder rerank blends cosine (0.7) with keyword score (0.3).
  • Service: FastAPI — POST /ask, POST /ask/stream (SSE, validate-before-stream), POST /analyze (agent), GET /demo, GET /health (index size, rules hash, staleness), GET /metrics (cost, p99, index).
  • MCP server: JSON-RPC 2.0 over stdio with four tools — adjudicate_statistical_claim, check_survey_comparability, lookup_verified_ground_truth, get_survey_metadata. Arg schemas validated before dispatch.
  • Policy agent: decomposes compound inquiries into atomic claims, adjudicates each, and synthesises a typed PolicyBriefing (governance status, integrity score, risk scorecard, defensible-phrasing recommendation) using five defence layers (L1 untrusted delimiters → L5 citation integrity).
  • Demo UI (demo.html): a single self-contained file — editorial theme, example chips, verdict cards, citation cards, coverage note, frozen hash line, history, health badge. No build step, offline-safe.

3. The independence mandate #

Goal: the new project must stand alone. It must not import from aip-lab/ or the shared aip toolkit, and it must not read files under the aip-lab tree at runtime. Clone the behaviour, not the dependency.

3.1 Current coupling inventory (what to replace)

Vidhi v1 borrows these utilities from the course toolkit. Each is small; reimplement or vendor each into the new package under vidhi_next/core/ (or a small internal _vendor).

3.2 Independence rules (acceptance)

  • Zero occurrences of import aip, from aip, or any path containing aip-lab in the new codebase. Add a test that greps the source tree and fails on any match.
  • The package installs and runs from a clean checkout with no network: pip install -e ".[dev]" then the full test + eval suite must be green offline.
  • Data (PDFs, store, rules, golden set) is copied into the new repo (or re-fetched by the new repo’s own fetcher) — never read from aip-lab/.
  • A single command runs everything: make verify (ingest → audit → build store → eval → tests). Non-zero exit on any failure.

6. The deterministic spec (the judge) #

This is the part that must be reproduced exactly. It is deliberately small, explicit and boring — that is the point.

6.1 Adjudication algorithm

def adjudicate(claim) -> Verdict:
    for stage in (scope, safety, comparability, metadata):   # fixed order
        v = stage(claim)
        if v is not None:
            return v.freeze(claim, rule_version)             # first rule fires
    if claim.extraction_confidence < 0.60 and claim.claim_type != "definitional":
        v = numeric(claim)
        if v.decision == "PASS":
            return warn(WARN_LOW_CONFIDENCE, R_LOW_EXTRACTION_CONF).freeze(...)
        return v.freeze(...)
    return numeric(claim).freeze(claim, rule_version)

6.2 Stage semantics (authoritative behaviour to clone)

  • Scope: REFUSE R_FORECAST if wants_forecast/claim_type==forecast; R_CAUSAL for causal; R_POLITICAL for political judgment; R_MICRODATA for individual/household microdata; R_SCOPE_OUT when the question is unanchored to the corpus.
  • Safety-A: REFUSE R_PROMPT_INJECTION when injection signals are detected in the question. (Refine with the calibrated classifier in §9.)
  • Comparability: evaluate the set of surveys referenced (claim survey + comparison surveys) against versioned rules and emit the matching WARN/REFUSE with the rule’s verbatim caveat. Poverty/real-change across the HCES 2011-12 break is a REFUSE; a plain level comparison is a WARN. Status-mix (usual vs CWS) and EUS-vs-PLFS get their own WARN codes.
  • Metadata: skip for definitional claims; otherwise validate survey → indicator → measure → allowed disaggregations (sex/residence/state/activity/age_group). Unknown or unsupported → WARN with a named code. Round compatibility is intentionally not checked here — the strict store lookup enforces it (no row for that round → WARN_NO_DATA).
  • Numeric: definitional → PASS_METHODOLOGY_ONLY. Asserted two-value pairs → verify each round cell-by-cell (R_NUMERIC_MISMATCH on disagreement, else PASS). Same-survey split comparison (rural vs urban, male vs female) → answer every verified side. Otherwise store.lookup: a user-asserted figure is compared (R_NUMERIC_MISMATCH on mismatch); a found row → PASS_WITH_NUMBER; no row → WARN_NO_DATA.

6.3 store.lookup strictness (subpopulation reification guard)

  • Only verification_status == "verified" rows are ever considered.
  • Survey and indicator must match. If the claim names a round, the row’s round must match.
  • For residence/sex/state/geography/activity: if the claim leaves a field unspecified it prefers the aggregate row; if the claim specifies a value, the row must match it — an all-India row can never answer a state/sex slice. Prefer the row with the most specified fields, then the most aggregate remaining.
  • For measure/age_group: match when both are specified; unspecified on either side is allowed.
  • Invariant test: a national figure must never be returned for a state/sex query; a confident wrong subgroup number is worse than a WARN.

6.4 Field-guarded semantic cache

  • Exact cache: normalized-question key → full response (~0 ms).
  • Semantic cache: cosine similarity over canonical Claim JSON proposes a hit, but reuse happens only if field_compatible(a, b) — every CRITICAL_FIELD that both sides specify agrees exactly. Confirmed empirically: danger and paraphrase ranges overlap (danger 0.80–0.97 vs paraphrase 0.78–0.95 on bge-small), so no threshold isolates danger pairs. The field-guard is the safety, not the threshold.
  • Test: 0 collisions across the danger set at every tested threshold, canonical and pipeline.

    note: "superseded round; kept for round-mismatch guard"

6.7 Consistency attribution rules (post-retrieval; downgrade only)

A retrieved excerpt may downgrade PASS → WARN_NUMERIC_MISMATCH only on genuine disagreement: same round AND same filters AND same measure basis AND same unit. Every rule below exists because a real incident proved the naive version wrong — reproduce them all:

  • Percent-gap figures (“difference as % of rural MPCE: 69.7”) are not currency levels (unit screen).
  • In “2022-23: … 6,459. 2023-24: …” lists, a number belongs to the preceding round token, not the nearer following one (segment ownership).
  • An excerpt silent on imputation basis cannot contradict a with/without-imputation claim (unknown is never contradiction).
  • Activity-aware for TUS: a same-sex number for a different activity is not a contradiction unless its activity anchor is near.
  • Plural tolerance (“Females spent 289” matches “female”); small counters (“7 days”, “Table 7”) are not figures; calendar years are not figures.
  • Pair claims (two-round) are verified cell-by-cell in rules, never by single-round excerpt attribution.

7. Data & corpus plan #

7.1 Source principles

  • Machine extraction, no hand-typed values. Every value comes from a parser that reads the source PDF/API; each carries cell provenance (document, table, page, sha256).
  • Raise, don’t guess. A parser that cannot find its anchor raises (layout drift), rather than guessing. The audit gate catches everything else.
  • Dual-source where possible. When two independent channels (e.g. a PDF parser and the live eSankhyiki API) cover the same cell, they must agree exactly; disagreement fails the build.
  • Release-time vs query-time. Live/internet ingestion happens at build time only; the query path is offline against the frozen store.

7.2 The coverage-scaling ingestion engine (P0, A0.3)

The single most valuable piece of “advanced” work: make adding data a data problem, not a code problem.

  1. Parser registry. Each source module declares its tables and exposes records(raw_dir) → (rows, manifest). The build script iterates the registry; no orchestration changes per source.
  2. Template families. Group parsers by table shape (e.g. “state × rural/urban two-column”, “round header + 9-value block”, “sentence-anchored highlight”). One robust template serves many tables.
  3. Verification by construction. Where a table has a known cross-check (e.g. an all-India total, or an API twin), assert it inside the parser so drift fails loudly.
  4. Coverage dashboard. Emit, per build, a report of verified rows by survey/indicator/slice and the golden-set coverage %, so growth is visible and regressions are obvious.

Definition of “scaled”: add a new survey family (parser + registry entry + a handful of golden cases) and the golden-set coverage rises, with the firewall, store and rules unchanged. If adding data ever requires editing adjudication logic, the abstraction is wrong.

7.3 Provenance & audit gate (must clone exactly)

  • Each candidate row is checked: the value must sit near its anchor (an indicator/table phrase for national rows; the state name for state rows), using tolerant numeric variants (4122, 4,122, 4122.0).
  • Unreadable source, untraceable value, or duplicate row id → build failure (non-zero exit).
  • Every row is frozen with an audit_note explaining why it is trusted.

9. New capability specs #

9.1 Calibrated Safety-A P0

  • Interface: safety.check(text) → {flagged, signals, score, mode}; the firewall treats flagged & “override” as the REFUSE trigger, exactly as today.
  • Baseline: keep the transparent, testable rule/regex detector as the offline default.
  • Classifier: a small local model or a well-specified scoring function, with a committed red-team set (≥100 injections of many families: override, role-switch, exfiltration, encoded blobs, tool abuse) and ≥100 benign questions (including statistics questions that merely mention instructions).
  • Report: precision, recall, F1 with CIs; the operating point chosen for a target recall; both modes compared side by side.

9.2 LLM translator, translate-only P0

  • The LLM maps NL → the exact Claim keys and never touches the verdict. Output is schema-validated; any failure falls back to the heuristic.
  • Include the tolerant JSON repair loop (strip fences, extract object, fix trailing commas/single quotes, default invalid enums).
  • Measure on a labelled paraphrase set against the heuristic; ship whichever wins, with the other as fallback. Off by default; never required for the core path.

9.3 Explainability & audit log P1

  • Append-only JSONL audit log: one record per ask (redacted question, trace_id, claim, stage that fired, decision/sub/reason, row_id used, rule_version, frozen_hash, latency).
  • vidhi verify <trace_id> (CLI) or GET /verdict/{trace_id} recomputes the frozen hash from the stored claim+verdict+rule_version and confirms equality.
  • The demo UI gains a “why this verdict” panel: the rule that fired, its verbatim caveat, and the source cell.

9.4 Freshness, signed manifest, deployment P1

  • Manifest carries built_at, source sha256 list, rule version, row count, and a signature/hash. /health exposes staleness days and flips stale past the threshold.
  • Container build bakes the store; startup pre-warms the embedder (no first-query cliff). TLS verification on for any live source; secrets from a manager, never .env in production.

9.5 Service v2, SDK, CLI P1

  • Versioned REST (/v1/ask, /v1/ask/stream, /v1/analyze, /v1/health, /v1/metrics, /v1/verdict/{id}) with a committed OpenAPI schema.
  • Typed Python SDK returning the same Response object as the service; a vidhi CLI with ask, verify, eval.
  • MCP server keeps the four tools; add verify_verdict and explain_verdict.

11. Non-goals, honest limits & risks #

11.1 Non-goals

  • Not a general-purpose chatbot or a rival retrieval assistant. It is a governance/sourcing layer that other assistants can plug into. REFUSE is reserved for speculation, politics and injections — never for an answerable number.
  • Not a forecasting or causal-inference engine.
  • Not a microdata de-anonymiser (re-identification is refused by design).
  • Not a promise of full-catalog coverage on day one. Coverage is the honest limit; the architecture removes the ceiling.

11.2 Known limits to carry forward (be honest)

  • Coverage is the limit, not logic: uncovered slices return WARN_NO_DATA — never a guess. Scaling the corpus is the main value-add.
  • Heuristic extraction misreads exotic phrasing (plural/casing, UTs); the LLM translator must be measured, not assumed.
  • Any live API source inherits its transport’s weaknesses; keep the query path offline and verify TLS at release time.
  • Semantic cache above any cosine threshold is unsafe; only the field-guard makes it safe (state this in the docs).

11.3 Risks & mitigations

D. Glossary

  • PASS / WARN / REFUSE — the three verdicts.
  • Frozen hash — SHA-256 over claim + verdict + rule_version, computed before retrieval (Safety-B).
  • Evidence tier — VERIFIED (frozen store) / SOURCED (live, labelled) / NONE.
  • Danger pair — two questions differing only in a critical field (e.g. urban vs rural) that must never share a cached answer.
  • Field-guard — deterministic exact match on critical fields; the cache’s real safety mechanism.
  • Wilson CI — confidence interval for a proportion, used for every reported rate.
  • MCP — Model Context Protocol; lets other AI assistants call Vidhi as a governance tool.
