Vidhi Next v2 — closing the seams between rules and reality

Vidhi v1 proved a deterministic firewall can hit 100/100 on its own golden set. This revision audits the seams that score does not cover — a verdict hash that doesn't bind the number, a cache rule that could smuggle aggregate answers into slice questions, injection detection that only speaks English (and only fires on one of six signals), comparisons with no notion of sampling error — and specifies the fixes, plus the measured adoption of every candidate technique (fine-tuning, embeddings, GNN, RNN, JEPA, conformal, formal methods) strictly inside the six guarantees — and sets the bar MoSPI's own published AI stack (StatDoc AI, the eSankhyiki semantic search, the website chatbot, the MCP beta) cannot meet by construction: verified adjudication, with a head-to-head benchmark to prove it.

Assembled from: the v1 spec, the v1 evaluation numbers, an interrupted external review (Oct 2026 — research and statistics salvaged, delivery completed here), and the demo v2 referenced alongside this document (commit it alongside so the claims can be verified; it is not part of the v1 baseline repo). All numbers carry provenance marks (§0).

0. How to use this document #

This is the authoritative brief for the next build, superseding v1 of the spec. §1 is the audit (what is actually wrong, ordered by severity). §2 places each problem against what frontier labs and national statistical offices now ship. §3 triages every proposed technique into planes — judge (forbidden to learned models), proposer, evidence, offline tooling, or reject — with honest "this does not help" rows. §4–§9 turn that into architecture, judge deltas, data, evaluation gates, phases, and the API/UI contract. §11 has paste-ready prompts.

1. Audit: the seams #

Vidhi's headline numbers are real — and they measure the wrong edges. 100/100 on the golden set proves the rules fire as authored; it does not prove the store is authentic, the cache is safe under reuse, injections in Hindi are caught, or a 0.8 pp difference is a real difference. The seams below are grouped by severity class (S1 > S2 > S3) and ordered within each. F1–F7 are architectural seams; F8 is a demo defect already fixed in the v2 UI; F9–F11 are capability gaps — the classes of silent misanswer that neither v1 nor MoSPI's own discovery stack prevents, and the price of admission for beating the incumbent (§2A). Each carries evidence, a fix, and a test ID that recurs in §7's gates.

F1 · The integrity gap: the hash proves the verdict, not the number #

frozen_hash = sha256(claim ⊕ verdict ⊕ rules) is computed before retrieval — exactly right for prompt-injection non-interference (guarantee 2). But the response's figure is read from the store afterwards. Nothing cryptographically links the number you see to the hash you can verify. A tampered store.json, a forked build, or a man-in-the-middle on the API can swap 3,788 for 4,500 and the frozen hash still "validates."

Fix (two hashes, one signature). (1) The store manifest hash is known pre-retrieval, so fold it into the frozen payload — the verdict now binds to a specific store generation. (2) Add a post-retrieval figure attestation: sha256(frozen_hash ⊕ row_id ⊕ value ⊕ unit ⊕ row.pdf_sha256 ⊕ row.page). (3) Sign the manifest (Ed25519 or ECDSA P-256 — the demo's WebCrypto can verify the latter in-browser today). Clients verify three things: manifest signature → frozen hash → attestation. Spec in §4.

Test T-TAMPER: flip one value in a forked store; the client verify path must fail closed. Poison-invariance (T-POISON, §7) already covers the verdict; this closes the number.

Rebuild side-effect (state it explicitly). Because the frozen hash now binds store_manifest_sha256, every store rebuild changes every frozen hash even when the verdict is unchanged. That is correct for integrity, but it means the positive semantic cache — not only the negative cache — is invalidated on rebuild. Handled in §4.6.

F2 · Cache reuse is one-sided — latent today, live the moment serving is wired # verify-in-code

The field-guard reads: reuse when "every CRITICAL_FIELD that both sides specify agrees exactly." In code (claims.py) that is literally if va is None or vb is None: continue. So a cached claim with residence=null (all-India) is "compatible" with a new claim with residence="urban", because "urban" is specified on one side only. That is exactly the failure the reification guard exists to prevent.

The nuance that changes the framing. In v1 the semantic cache never serves an answer: _semantic_guard()'s result is written only into cache_info.semantic; the only cache that returns a response is the exact (normalized-question) cache. So today an aggregate verdict cannot actually answer a slice query through the pipeline — the defect is latent. It becomes live the moment v2 wires the semantic cache to serve (which is the intent). Fix it before wiring, not after.

Why the existing tests miss it. compatible() is exercised in eval.py's danger-pair check — but there both sides specify the differing field (urban vs rural), so the one-sided null path is never hit.

Fix. Reuse iff canon(claim_new) == canon(claim_cached) — exact equality including the null-vs-specified distinction (nulls are meaningful: they mean "asked for the aggregate"). Cosine is kept only as a candidate-finder (propose). Add a negative cache for WARN_NO_DATA verdicts — same canonical key. Critical detail: the negative-cache key must include the store_manifest_sha256, so every store rebuild (new coverage!) invalidates cached refusals. Otherwise fresh coverage can never reach users who asked before it landed.

Test T-MSLICE: for every (general, specific) pair, responses must differ or the specific one must be a genuine slice answer; 0 violations.

F3 · Safety-A: English regex on an open set — and only one signal fires #

Three problems compound: regexes miss paraphrased injections; they are English-only while the user base writes Hindi and Hinglish; and detection is framed as an open-set classification problem ("is this an attack?") when the stronger frame is closed-set claim parsing — the translator may only emit a fixed schema over a fixed enum, so instruction-like text simply fails to produce a valid claim and can never steer the judge. Detection then becomes a backstop, not the load-bearing wall.

Sharper fact (verified in code). It is not merely "English regex." v1's firewall refuses only when "override" in v.signals (rules.py). detect_injection emits six signal classes — override, role_switch, exfiltration, delimiter_break, tool_coercion, encoded — and the other five are computed and then ignored. So today's posture is "English regex, and 1 of 6 signals actually blocks." Blocking on the full signal set is a one-line change; measuring the other five is a red-team task.

Fix (cascade). L0: closed-set schema-constrained translator (parse failure → WARN_LOW_CONFIDENCE, never a guess). L1: transparent regex baseline (kept, it's auditable) — now honouring all six signal classes mapped to explicit reason codes. L2: a small open-weights injection/jailbreak classifier at CPU scale — the LlamaFirewall / Prompt Guard 2 line ships 22M/86M-parameter classifiers exactly for this; the 22M is English-only (DeBERTa-xsmall) while the 86M is multilingual (mDeBERTa, evaluated on Hindi among 8 langs), so use the 86M for Hindi/Hinglish or fine-tune a MuRIL student for CPU. Report P/R with CIs on our own committed set. Vendor block rates are ceilings, not evidence.

F4 · No sampling-error layer #

The comparability stage catches design breaks (HCES 2011-12 → 2023-24 redesign) but nothing catches statistical non-distinguishability. A 0.8 pp round-over-round difference in a rate whose s.e. is 0.3 pp is not a change; v1 would PASS it with both cells verified. Where MoSPI publishes standard errors or confidence intervals, carry them in the store; where it does not, say so visibly ("s.e. not published") rather than implying precision.

Fix. Store rows gain se (nullable). The Numeric stage's pair-verification gains one rule: if |Δ| < 1.96·√(se₁² + se₂²), emit WARN_STATISTICALLY_INDISTINGUISHABLE — both verified figures shown, no trend endorsed. This changes verdicts, so the comparability rule file bumps to version: 4 and the golden set gains pair cases with expected WARNs. Demo v2 already implements the UX; the store and rules must catch up.

Assumption & false-positive risk (state it). The guard assumes the two rounds are independent samples. With design effects, cluster sampling and rounding it can emit false WARNs where a real change exists. So: publish the assumption next to the rule; when either se is null, skip the guard and print "s.e. not published" (no silent precision); and log every guard-triggered pair to a review queue so the threshold can be recalibrated. Test T-DISTINGUISH.

F5 · Evaluation power and metric naming #

0.676Wilson lower, refusal 8/8 M — the reported "floor 0.68"
31.2%one-sided 95% upper bound on the miss rate at n=8 C — the same data cannot rule out a 31% miss rate
14.6%zero-failure upper bound at n=19 danger pairs C

The honesty of reporting [0.963–1.000] on 100/100 is right; the problem is the sets are too small to say more. On the metric itself: "54/173 (31.2%) store coverage" is defined in v1 — eval.py computes len(touched_row_ids) / verified_rows, i.e. verified rows touched by golden figures ÷ total verified rows. The defect is the name: "coverage" reads as answerability but measures row utilization. Worse, v1's own documents disagree on the denominator — CONF_AI_PAPER.md reports 54/101 (53.5%), EVALUATION_REPORT.md reports 54/173 (31.2%). Fix the definition: primary coverage = golden questions that can PASS from the store ÷ all golden questions; row-utilization is a secondary diagnostic; report both per build, consistently. Then scale: refusal ≥300 cases, danger pairs ≥1000 (bounds in §7).

F6 · Dead-ends, disambiguation, language #

At 31.2% row utilization, most users hit WARN_NO_DATA — a refusal with no next action. Three fixes: (a) nearest-covered-slice suggestions (shipped in demo v2 — the GNN-lite version; §3); (b) a one-question disambiguation protocol from the text-to-SQL line (expected-information-gain): when a claim is under-specified and ≥2 verified slices match the other fields, ask exactly one question ("rural, urban, or both?") instead of guessing the aggregate; (c) Hindi + Hinglish via MuRIL — the real register of Indian policy questions is code-mixed, and MuRIL is built for exactly that robustness. Test T-CLARIFY.

F7 · Operational seams #

  • Race conditions: concurrent exact/semantic cache writes and metrics counters need single-writer or atomic-swap discipline; add a concurrency test at 20 workers (T-CONCUR).
  • Numeric tolerance is undefined: "exact match" needs a spec — decimal-normalized equality, unit-screened, imputation legs never "close enough" to each other (T-TOLERANCE).
  • Single-source API twin: eSankhyiki MCP becomes the second channel (§2, §6) — but wrap it with timeouts and never let it block the offline path.
  • Parser licensing: before vendoring any table/PDF parser (Docling, pdfplumber, Camelot, Table Transformer), check license compatibility with the repo's terms; record the decision in docs/.

F9 · Definitions are not locked — the "jobless" trap #

MoSPI's own semantic-search manual motivates its tool with the query "What percent of people were Jobless in Villages in 2022-23" and its solution is to map such phrasing to the closest indicator and auto-apply filters V. That is a relevance engine, not an adjudicator: if the user meant Current Weekly Status unemployment rather than UPSS, a ranked redirect delivers whatever it ranked first — silently. PLFS figures differ materially by activity status (UPSS vs CWS vs CDS) and population base (15+). A system that does not force a question to resolve to exactly one defined indicator cannot be accurate; it can only be relevant.

Fix. Claim schema v2 gains status_variant (UPSS/CWS/CDS), measure_type (rate/share/count/pp/index) and population_base; the closed-set translator must emit them or hand back one EIG clarify question; otherwise WARN_AMBIGUOUS_DEFINITION / R_AMBIGUOUS_DEFINITION. Never nearest-match. The incumbent's own example becomes golden case #1. Test T-DEFLOCK.

F10 · No vintage discipline — revisions are invisible #

PLFS estimates are revised across releases; NAS ships Advance, Provisional, Revised and Final vintages; IIP and CPI are revised on fixed schedules; base years change. Quoting a superseded figure as current is a silent factual error no relevance score catches — and MoSPI's chatbot refreshes its knowledge base "in line with ministry-defined schedules" V, so between refreshes it can serve stale content with no as_of stamp at all.

Fix. Store rows gain vintage, as_of, revised_from (a supersession chain) and base_year. Default = latest vintage, always stated in the response. Cross-vintage comparisons quote both vintages or refuse (R_VINTAGE_MISMATCH). When a question pins a period whose vintages differ materially, ask which vintage is meant — one question, then the aggregate-with-note rule as ever. Test T-VINTAGE.

F11 · Footnotes don't travel with the number #

MoSPI tables carry footnotes — states excluded, provisional marks, sample caveats, definition notes. A number stripped of its footnote is a different fact. v1 drops them at ingest.

Fix. Ingest footnotes per table/cell with the same provenance discipline as values; the response renders them adjacent to the figure; a PASS requires footnote display; a footnote that materially qualifies a claim answers with R_FOOTNOTE_BOUND. Test T-FOOTNOTE (deterministic, 100%).

What "beating" means, precisely. Not breadth — the incumbent wins discovery breadth (21+ products, the whole portal).   1. Definition ambiguity — "jobless in villages" (status variant, measure type, population base);

  3. Series breaks — HCES 2011-12 → 2022-24 redesign, base-year changes;

The strategic read. MoSPI shipping an MCP server is the best possible validation: access is now a commodity; whether you may say the number is not. And the stack above shows MoSPI has occupied discovery, not adjudication: nothing in their published design verifies a claim, states a vintage, quantifies sampling error, or refuses. That seat is empty. Vidhi takes it — on top of MoSPI's own data rails — and keeps it by publishing the measured record (T-INCUMBENT, transparency log) rather than asserting superiority.

4.2 Dual hash and signature (F1 fix)

manifest = {rows, rule_version, built_at, row_count}
manifest_sha256 = sha256(canonical_json(manifest))
manifest_sig    = sign(manifest_sha256, Ed25519 | ECDSA-P256)   # WebCrypto-verifiable

frozen_hash        = sha256(canon(claim) ⊕ [decision, sub_code, reason_code]
                          ⊕ rule_version ⊕ manifest_sha256)[:16]      # pre-retrieval
figure_attestation = sha256(frozen_hash ⊕ row_id ⊕ value ⊕ unit
                          ⊕ row.pdf_sha256 ⊕ row.page)[:16]           # post-retrieval

client verify: manifest_sig → frozen_hash → figure_attestation  (fail closed)

Tests: (a) T-TAMPER — mutate one value in a forked store, client verification must fail; (b) T-POISON — frozen hash unchanged across ≥1000 injected variants (bound: miss-rate upper 0.30% C at 95%); (c) demo v2's in-browser recompute extends to the attestation line. Note: because the frozen hash binds manifest_sha256, a store rebuild changes every frozen hash by design — this is what invalidates the positive semantic cache as well as the negative one (§4.6).

4.3 Translator (closed-set) spec

  • Output is a fixed JSON schema; every categorical field validated against the taxonomy enum (surveys, indicators, states, measures). Enum-invalid output is discarded, never coerced.
  • Confidence = conformal-calibrated score; optional JEPA probe contributes an OOD channel (adopted only if it beats the temperature-scaled baseline — §3).
  • Parse failure or enum failure → WARN_LOW_CONFIDENCE with suggestion chips. Injection text reaches neither judge nor store.
  • Heuristic translator retained as fallback; LLM participates only when measured better on the labelled paraphrase set.

4.4 Disambiguation protocol (F6 fix)

  • Trigger: claim under-specified on a slice field (residence/sex) AND ≥2 verified slices match the remaining fields.
  • Ask exactly one question — the field with the highest expected information gain (which option most reduces the candidate set). Response gains clarify:{question, options[]}.
  • One round max; after that, answer the aggregate with its note. Never guess. Test T-CLARIFY.

4.5 SOURCED tier via eSankhyiki MCP (F6 fix, honest)

  • On WARN_NO_DATA and VIDHI_OFFLINE=0: query the official MCP/API, label the result SOURCED — sourced, not certified, show retrieval timestamp + doc id. Never upgrades to PASS; never enters the verified store without passing the audit gate.
  • Dual-source rule gains a second channel: overlapping cells must agree across PDF parsers and the MCP, else build fails.
  • Dependency hygiene: pinned client, hard timeout, circuit breaker, offline path never blocks.

4.6 Concurrency & cache discipline (F7 fix)

  • Exact/semantic caches: single-writer with atomic swap (write-temp-rename); in-process LRU behind a lock. Test T-CONCUR at 20 workers.
  • Metrics: atomic counters only.
  • Negative cache invalidated by store_manifest_sha256 change (new coverage must reach re-askers).
  • Positive cache is invalidated too. Since the frozen hash binds manifest_sha256 (§4.2), a store rebuild changes every frozen hash even for an unchanged verdict; the positive semantic cache must therefore be keyed/versioned by store_manifest_sha256 as well, and never serve a pre-rebuild frozen hash.

4.7 Definition-locking, vintage and footnotes (F9–F11 fixes)

  • Claim schema v2: status_variant ∈ {UPSS, CWS, CDS, n/a}, measure_type ∈ {rate, share, count, pp, index}, population_base, period (explicit fiscal-year semantics; PLFS runs July–June), vintage_requested. Enum-validated by the closed-set translator like every other axis.
  • Unresolvable definition → one EIG clarify question or WARN_AMBIGUOUS_DEFINITION / R_AMBIGUOUS_DEFINITION. Never nearest-match — that is the incumbent's failure mode, not ours.
  • Store rows v2: vintage, as_of, revised_from (supersession chain), base_year, footnotes[], status_variant. Latest-vintage default, always displayed; supersession chains traversable ("show the revision history of this cell").
  • Cross-vintage comparisons quote both vintages or refuse (R_VINTAGE_MISMATCH); never mix vintages inside one trend claim.
  • Footnotes render adjacent to the figure, always; PASS requires footnote display; a material qualifier answers with R_FOOTNOTE_BOUND.
  • Unit discipline: units stored in a fixed enum; lakh/crore/thousand/million conversions happen only at render; pp vs % enforced by measure_type.

5. The judge v2 — small, boring, now machine-checked #

The five stages, fixed order, first-rule-fires: unchanged. Four deltas:

  1. Numeric stage, pair branch: after cell-by-cell verification, apply the distinguishability rule — |Δ| < 1.96·√(se₁²+se₂²) → WARN_STATISTICALLY_INDISTINGUISHABLE (sub-code), R_SE_NOT_DISTINGUISHABLE (reason). If either se is null (not published), skip the guard but the response must say "s.e. not published."
  2. Bump the rule data to version: 4. In v1 the emitted rule_version is not a sequence integer — it is a computed sha256([rules_blob, row_count])[:12] hash — while comparability_rules.yaml carries an integer version: 3. So the change is: bump the YAML version: 3 → 4; the derived rule_version hash then changes by construction. Golden set v2 adds pair cases with expected WARNs; parity with v1 is reported per-rule so the delta is visible, not hidden.
  3. Rules become a DSL, checked by SMT (Cedar/SymCert-inspired): CI asserts (a) determinism — the ordered evaluation never yields two verdicts; (b) reachability — no rule is permanently shadowed; (c) the reason_code → (decision, sub_code) mapping is functional — which requires first splitting the one v1 code that maps to two verdicts: R_COMPARABILITY_HCES_METHOD currently returns (WARN, WARN_COMPARABILITY) for a plain level comparison and (REFUSE, REFUSE_COMPARABILITY) when the claim asserts poverty or a real change. Give the refusal branch its own code (e.g. R_COMPARABILITY_HCES_POVERTY_REFUSE); this split is part of the version: 4 change. (d) stage order is a total order. A mutant-rule test (inject a conflicting rule) must fail the check.
  4. Scope stage gains the definition and vintage lock (rules in the same version: 4 data): reason codes R_AMBIGUOUS_DEFINITION, R_VINTAGE_MISMATCH, R_FOOTNOTE_BOUND; the closed-set translator must emit the new axes or return a clarify. The five-stage order is untouched — these are rules inside Scope, checked by the same SMT properties (determinism, reachability, functional reason codes).

Reification guard — now enforced at the cache too. An all-India row can never answer a state/sex/urban slice, and a cached aggregate verdict can never serve a slice question (F2). Both are the same invariant, tested by the same property (T-MSLICE).

6. Data & corpus plan v2 #

  • se/CI sourcing: harvest published standard errors / margins alongside values where MoSPI prints them; se:null otherwise, and the UI shows "s.e. not published" instead of silence. Never impute an s.e.
  • Dual-source: PDF parsers + eSankhyiki MCP; exact agreement on overlap or build failure. The MCP is pinned and timeout-wrapped.
  • Parser selection: benchmark Docling / pdfplumber / Camelot / Table Transformer on our own corpus (cell-level accuracy + provenance traceability); record license compatibility before vendoring. Benchmark results vary sharply by table shape — trust our corpus's numbers, not vendor blogs.
  • Coverage metric (defined, consistently): primary = golden questions answerable PASS from the store ÷ all golden questions; secondary = row utilization (touched_row_ids / verified_rows, the number v1 mislabelled "coverage"). Report both per build; regressions block merge. v1's own docs must be reconciled to a single denominator (the 101-vs-173 discrepancy, F5).
  • Coverage planner: GNN over the claim-ontology graph, ranked by query-log demand + suggestion-click logs, proposes the next 500 slices to ingest. Data problem, not code problem — adding slices must never touch the firewall.
  • Break quantification (offline): state-space intervention analysis (Statistics Norway's LFS-2021 methodology) estimates the size of the 2011-12 → 2022-24 discontinuity; the estimate (with CI) becomes a field in comparability_rules.yaml version 4 — the caveat gains a measured magnitude.
  • Vintage harvesting: every ingested cell is tagged with its release vintage (Advance/Provisional/Revised/Final), as_of and its supersession link; the ingest pipeline must refuse a release that would leave existing rows' vintage ambiguous.
  • Footnote capture: table and cell footnotes are extracted with the same provenance discipline as values — the parser benchmark must score footnote traceability, not just cell accuracy.
  • Definition registry: each indicator maps to its statistical definition — activity status, population base, measure, and the report page that defines it — versioned with the rule data and shared by translator and judge.
  • Base-year registry: index series (CPI, IIP, NAS deflators) carry their base year and link to comparability rules for cross-base questions.

Metamorphic relations (run over ≥10k generated cases)

  • M1 · paraphrase invariance (T-PARAPHRASE): paraphrase → identical canonical claim → identical verdict.
  • M2 · field-swap sensitivity (T-MSLICE): changing a slice field must change the answer row or trigger a coverage note — never return the same figure.
  • M3 · poison invariance (T-POISON): injected corpus variants leave the frozen hash unchanged (data non-interference, CaMeL-style property).
  • M-slice · aggregate-never-answers-slice (T-MSLICE): for every (general, specific) question pair, the specific answer differs or honestly warns.
  • M4 · tolerance monotonicity (T-TOLERANCE): equal values pass, perturbed values fail, at the specified tolerance; imputation legs never cross.
  • M5 · definition-swap sensitivity (T-DEFLOCK): swapping status_variant or measure_type must change the resolved row or trigger a clarify/WARN — never return the same figure.
  • M6 · vintage monotonicity (T-VINTAGE): a newer vintage supersedes the older; answering from an older vintage without an explicit as-of request must be impossible.

The head-to-head suite (T-INCUMBENT)

300 committed adversarial questions — 50 per class of the six failure classes in §2A — run identically through Vidhi and the incumbent's public surfaces (the eSankhyiki semantic-search beta and the website chatbot). Graded blind against a fixed rubric: number correct, definition correct, vintage correct, footnotes shown, uncertainty stated, refusal appropriate. Wilson 95% CIs on both systems; per-class breakdowns published. Interface drift is handled by re-baselining each quarter. Nothing behind a login (StatDoc AI) is scraped — if it cannot be measured publicly, it is not quoted at all. Results ship with the P2 community benchmark.

10. Non-goals, limits, risks #

  • Never: learned verdicts, cosine-threshold safety, silent SOURCED→PASS upgrades, imputed standard errors, auto-applied critic changes.
  • eSankhyiki dependency: official MCP is a beta; pin schemas, timeout, circuit-break; the offline deterministic path must never block on it. Strategically, if MoSPI's own assistant grows governance, Vidhi's niche narrows — the differentiator to defend is verifiable governance (hashes, logs, measured gates).
  • JEPA may lose: the pilot is timeboxed; a negative result with CI is a valid deliverable.
  • Vendor numbers are ceilings, not evidence: Anthropic's ~95% block rate V and benchmark leaders on FACTS Grounding motivate, never substitute for, our own measured gates.
  • Small-n honesty: until refusal n≥300, the honest claim is "8/8, miss-rate upper bound 31.2% C" — say exactly that.
  • Metric honesty: never call row-utilization "coverage"; report primary coverage and utilization separately and reconcile v1's 101-vs-173 denominator discrepancy before quoting either.
  • Source hygiene: §12 titles/orgs were retrieved in-session and the load-bearing ones re-fetched; re-verify every identifier before the paper deadline.
  • Benchmark ethics: the head-to-head uses only public interfaces, respects ToS and rate limits, and never scrapes behind a login (StatDoc AI); unmeasurable surfaces are not quoted at all. "Beats the incumbent" is claimed only from our own published numbers, with CIs — never from vendor material.
  • MoSPI may add governance later: if StatDoc AI grows adjudication, the defensible moat is the verifiable record — signed manifests, attestations, transparency log, published gates — not being first.
