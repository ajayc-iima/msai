The Problem

Parliamentary answers aren't blog posts.

They're legally binding government responses. An invented figure, a wrong ministry, a misquoted statistic — in this domain, hallucination isn't just annoying. It's dangerous.

The Core Questions

  • RQ1: Does dense semantic retrieval actually beat good old keyword search on bureaucratic text?
  • RQ2: Can the system enforce zero fabricated claims without giving up answer coverage?

The spoiler

The short answer: No to RQ1 (BM25 wins decisively). Yes to RQ2 — but only if you verify after generation with code, not by asking the LLM nicely.

Experiment 2 — Policy Design

Four policies. One question: when do LLMs stop hallucinating?

Policy D's rule is simple but absolute: After the LLM generates an answer, every claim is checked against its cited chunk. Does the text actually say that? Are the numbers exactly right? If any single claim fails — the entire answer becomes "I don't know." No exceptions.

Prompting is not security. Code is.

A → B: "Answer only from evidence" improved faithfulness dramatically. But 17% of answers still contained fabricated claims. The LLM just… ignores instructions sometimes.
B → C: Adding a pre-generation gate changed nothing. The gate catches missing documents — it can't detect lies within retrieved text.
C → D: Post-generation verification drove violations to exactly zero at only 0.1% coverage cost. One answer per thousand gets over-demoted. That's the price of safety.

Honest Mistakes

Things that didn't work. Because that's the interesting part.

Dense retrieval was basically random.
nDCG@10 = 0.082 vs BM25's 0.697. The 75.5% truncation tax + bureaucratic proper nouns that embeddings smooth away = near-random performance. A genuine negative result about what dense models can't do.
Our cost estimates were off by 10×.
I initially assumed 1–2k docs/sec for encoding. Reality: 1.4 seq/s on CPU. Full chunked dense would take 9.5 hours. Lesson learned: measure throughput on 200 docs before planning anything.
Two verification rules failed before v3.
v1: Token overlap demoted "thirty-two" (tokenization) and passed invented "40" (ignored numerals).
v2: Content containment broke on "inspected" vs "inspection."
v3 (LCS + trigram + numeric) finally works. Known weakness: year flips score 0.93 — only the numeric check catches them.
Reranking was a waste of CPU cycles.
Cross-encoder rerank: +0.0001 nDCG@10 at 6.26 seconds per query. That's 6,260× slower for no measurable improvement. On GPU it might help. On CPU, don't bother.

If I Had More Time

Five things I'd do next.

  • Human-written queries. Title-derived queries overstate every system. Real information needs like "which states received the most MGNREGA funding in 2023?" would stress retrieval far harder.
  • Full chunked dense on GPU. Head-only was a labeled baseline, not a claim. Full encoding takes 32h on CPU — under 30 min on a single GPU. That's where dense retrieval might finally compete.
  • Hindi cross-lingual retrieval. 23.6% of records contain Hindi text (422 rows, 158 usable). A bilingual embedding model could unlock this entirely ignored slice.
  • Table & annexure parsing. Many ministerial answers contain structured tables with state-wise statistics. A specialized parser would dramatically improve evidence extraction.
  • Measure throughput before planning. I shipped two cost estimates that were wrong by 10×. The fix: run encode(200_docs) before committing to anything.
Conclusions

Two questions. Two clear answers.

RQ1: Does dense retrieval help?

No. On formulaic parliamentary text, tuned BM25 scored nDCG@10 = 0.697 while dense head-only managed 0.082. The gap is -0.615 (95% CI: [-0.622, -0.609]). Proper nouns and acronyms are more discriminative than semantic similarity. This is a legitimate finding about bureaucratic language.

RQ2: Can the system enforce zero hallucinations?

Yes — but only with code-level verification, not prompting. Policy B (strict prompt) still had a 17% violation rate. Policy D (verify + demote) achieved 0.000% at 0.1% coverage cost. Prompt wording requests behavior. Code guarantees it.

The meta-lesson: The error budget waterfall (13.5% retrieval + 15.5% evidence + 0.0% generation = 71.0% success) shows the bottleneck is retrieval and chunking, not generation. Improving how we find and extract evidence would help more than any generation-side upgrade.
